================================================================================
              AI ISP CHATBOT — COMPLETE PROJECT EXPLANATION
================================================================================

This document explains every file inside application/ and traces a full
message scenario from user input to final output.


================================================================================
PART 1 — WHAT EACH FILE DOES
================================================================================

────────────────────────────────────────
1. APPLICATION ROOT
────────────────────────────────────────

__init__.py
  Package marker. Declares version ("1.0.0") and author metadata.

app.py
  THE entry point of the whole program. Contains the Application class that:
  - Bootstraps the system (creates config, creates ChatbotFacade, initializes it)
  - Supports two run modes:
    • Console mode — interactive terminal loop (type a message, get a response)
    • Telegram mode — connects to Telegram Bot API for real users
  - Has a main() CLI function that parses --mode, --knowledge, --debug args


────────────────────────────────────────
2. FACADE LAYER (application/facade/)
   The central coordinator — connects everything together
────────────────────────────────────────

chatbot_facade.py
  THE main orchestrator of the entire application. This is the single entry
  point that the presentation layer (Telegram/Console) calls.
  
  What it does:
  - Creates and holds ALL services (Session, Agent, RAG, CRM, LLM, Response, Analytics)
  - Wires up the ServiceDispatcher and WorkflowCoordinator
  - handle_message() runs the FULL pipeline:
      1. Get/create session for the user
      2. Ask the Agent to classify intent
      3. Execute workflow (RAG/CRM/both) via WorkflowCoordinator
      4. Build final response via ResponseService
      5. Save to session history
      6. Record analytics
  - Publishes events to the MessageBroker at key points

service_dispatcher.py
  A thin routing layer that delegates calls to the correct service.
  Methods:
  - dispatch_rag(query)         → calls RAGService.query()
  - dispatch_crm(operation)     → calls CRMService.execute()
  - dispatch_llm_rag(q, ctx)    → calls LLMService.generate_rag_answer()
  - dispatch_llm_crm(intent, d) → calls LLMService.summarize_crm_data()
  - dispatch_llm_combined(...)  → calls LLMService.generate_combined_response()
  - dispatch_greeting(msg)      → calls LLMService.generate_greeting()

workflow_coordinator.py
  Executes multi-step workflows based on agent decisions.
  - If no services needed (greeting): generates a greeting via LLM
  - If RAG needed: dispatches RAG query
  - If CRM needed: uses TaskPlanner to map intent→CRM operation, dispatches it
  - After collecting results, generates final LLM answer using whatever data
    was collected (RAG context, CRM data, or both)


────────────────────────────────────────
3. AGENT LAYER (application/agent/)
   The "brain" — decides WHAT is needed (not HOW to do it)
────────────────────────────────────────

agent_service.py
  The decision-making brain. Its analyze() method:
  1. Calls IntentClassifier.classify_decision() to get intent + required services
  2. Extracts parameters from the message (customer_id, query text)
  3. Returns an AgentDecision object (intent, requires, parameters, confidence)
  Also has build_response_instruction() for tone/language settings.

intent_classifier.py
  Classifies user messages into ISP-specific intents.
  Two classification strategies:
  1. LLM-based (primary): Sends a structured prompt to the LLM asking it to
     pick from ALLOWED_INTENTS and decide which services (RAG/CRM) are needed.
     The LLM returns JSON like {"intent": "billing", "requires": ["CRM"]}
  2. Keyword fallback: If LLM is unavailable, matches Arabic keywords to intents
     (e.g., "رصيد" → billing, "باقة" → wireless_packages)
  Also defines INTENT_SERVICE_MAP that maps intents to required services.

intents.py
  A simple list of all 30 ALLOWED_INTENTS (services, dsl_troubleshooting,
  billing, wireless_packages, bot_channel, etc.). Used to constrain the LLM
  so it only picks valid intent names.

task_planner.py
  Builds ordered execution plans from intent + required services.
  Maps intents to CRM operation names (e.g., "billing" → "get_billing").
  Creates TaskStep objects with order, service, operation, and dependencies.

workflow_selector.py  ⚠️ UNUSED FILE
  Was intended to map intents to services, but the IntentClassifier now
  handles this directly. Not imported or used anywhere in the project.


────────────────────────────────────────
4. SESSION MANAGEMENT (application/session_management/)
   Tracks user conversations across messages
────────────────────────────────────────

session_service.py
  Manages session lifecycle with MySQL persistence + in-memory cache.
  - create_session(): Creates a new ConversationContext, caches it, persists to MySQL
  - get_or_create_session(): Reuses existing session or creates new one
  - update_session(): Adds messages to history, trims if > max_history
  - cleanup_expired(): Removes sessions older than TTL
  - Falls back to memory-only mode if MySQL is unavailable

conversation_context.py
  Data class holding per-session state:
  - session_id, user_id, customer_id
  - history[] — list of {role, text, timestamp, metadata} messages
  - current_intent
  - Methods: add_message(), get_history_text(), is_expired(), update_intent()


────────────────────────────────────────
5. RAG LAYER (application/rag/)
   Retrieval-Augmented Generation — answers from knowledge base
────────────────────────────────────────

rag_service.py
  Main RAG orchestrator. Two phases:
  INITIALIZATION:
    1. Loads the XLS knowledge file using pandas
    2. Splits text into overlapping chunks (350 chars, 50 overlap)
    3. Embeds each chunk using SentenceTransformer (multilingual model)
    4. Stores embeddings in ChromaDB vector database
  QUERY:
    1. Calls DocumentRetriever to find similar chunks
    2. Passes results through Reranker to filter by distance threshold
    3. Uses ContextBuilder to assemble final context string
    4. Returns ServiceResult with context + documents

document_retriever.py
  Wraps ChromaDB vector queries.
  - Encodes the query using the same embedding model
  - Queries ChromaDB for n_results nearest documents
  - Returns documents, distances, and IDs

reranker.py
  Filters and sorts retrieved documents by relevance.
  - Removes documents with distance > threshold (default 25.0)
  - Sorts remaining by distance (lower = more relevant)

context_builder.py
  Assembles retrieved documents into a single context string for the LLM.
  - Concatenates documents up to max_context_length (1500 chars)
  - Truncates if needed to stay within limit


────────────────────────────────────────
6. LLM LAYER (application/llm/)
   Generates natural language responses
────────────────────────────────────────

llm_service.py
  Main LLM orchestrator combining prompt building + inference + parsing.
  Methods:
  - generate_rag_answer(question, context) — answers using RAG context
  - summarize_crm_data(intent, crm_data)  — summarizes CRM data for user
  - generate_combined_response(...)        — uses both RAG + CRM
  - generate_greeting(message)             — responds to greetings
  - generate_raw(prompt)                   — raw LLM call (for intent classification)
  - health_check()                         — checks if LLM backend is alive

prompt_builder.py
  Constructs Arabic prompts for different scenarios:
  - RAG_ANSWER_TEMPLATE: "أنت مساعد ذكي..." + context + question
  - CRM_SUMMARY_TEMPLATE: Summarize CRM data for customer
  - COMBINED_TEMPLATE: Both RAG + CRM context
  - GREETING_TEMPLATE: Friendly greeting response

inference_engine.py
  Manages the LLM inference pipeline.
  - Selects provider based on config: Gemini or Ollama
  - Routes infer() calls to the selected provider

gemini_provider.py
  HTTP client for Google Gemini REST API.
  - Sends prompts to Gemini via REST API with API key
  - Handles temperature, top_p, top_k parameters
  - Has health_check() to verify API key works

ollama_provider.py
  HTTP client for local Ollama LLM API.
  - Sends prompts to localhost Ollama server
  - Configures model, temperature, context window
  - Has health_check() to verify Ollama is running

output_parser.py
  Cleans and validates LLM outputs:
  - Removes excessive newlines
  - Strips "الإجابة:" prefix artifacts
  - Returns fallback message if output is empty


────────────────────────────────────────
7. CRM INTEGRATION (application/crm_integration/)
   Connects to the ISP's Customer Relationship Management system
────────────────────────────────────────

crm_service.py
  High-level CRM operations. Provides business methods:
  - get_balance(customer_id)
  - get_customer_info(customer_id)
  - get_tickets(customer_id)
  - create_ticket(customer_id, details)
  - get_packages()
  - get_billing(customer_id)
  All go through execute() which calls MCPClient and returns ServiceResult.

mcp_client.py
  Model Context Protocol bridge for standardized tool calling.
  - Defines available "tools" (get_balance, get_tickets, etc.) with endpoints
  - execute_tool() substitutes parameters into URL templates
  - Routes GET/POST to CRMConnector

crm_connector.py
  Low-level HTTP client for CRM API.
  - Currently runs in MOCK mode with built-in fake data
  - Mock data includes: customer balances, profiles, tickets, packages, invoices
  - When real CRM is available, sends actual HTTP requests with auth headers


────────────────────────────────────────
8. RESPONSE GENERATION (application/response_generation/)
   Formats the final response for the user
────────────────────────────────────────

response_service.py
  Main response orchestrator:
  - generate(): Takes LLM answer + service results → builds text → formats
    for Telegram → determines sources used → returns ChatResponse
  - Also has generate_error(), generate_greeting(), generate_goodbye()

response_builder.py
  Constructs response text from multi-source results.
  - Primary: uses the LLM answer directly
  - Fallback: if LLM fails, formats raw CRM data or RAG context
  - Last resort: returns the support fallback message

formatter.py
  Formats responses for Telegram output:
  - Truncates to 4000 chars (Telegram's 4096 limit)
  - Has default greeting/goodbye templates in Arabic


────────────────────────────────────────
9. ANALYTICS (application/analytics/)
   Tracks usage statistics
────────────────────────────────────────

analytics_service.py
  High-level analytics orchestrator:
  - record_interaction(): Records session, intent, services used, latency
  - get_summary(): Returns global stats
  - get_session_stats(): Returns per-session stats

usage_metrics.py
  Thread-safe in-memory statistics tracker:
  - Total queries count
  - Queries broken down by intent
  - Service call counts (how many RAG vs CRM calls)
  - Per-session stats
  - Uptime tracking


────────────────────────────────────────
10. PRESENTATION (application/presentation/)
    User-facing interface
────────────────────────────────────────

telegram_bot.py
  Telegram Bot integration using python-telegram-bot library.
  - /start command: Welcome message in Arabic
  - /help command: Lists available commands
  - /stats command: Shows usage statistics
  - Text messages: Sends typing indicator, calls facade.handle_message(),
    replies with response text


────────────────────────────────────────
11. MONITORING (application/monitoring/)
    Logging, metrics, and tracing infrastructure
────────────────────────────────────────

logger.py
  Structured application logger wrapping Python's logging module.
  - Supports plain text or JSON output format
  - Attaches context (session_id, user_id, trace_id) to log records
  - Singleton pattern: one logger per name

metrics_collector.py
  In-memory performance metrics:
  - Counters (request counts, error counts)
  - Gauges (current values)
  - Histograms (latency distributions with p50/p95/p99)
  - Thread-safe with lock protection

trace_manager.py
  Distributed tracing with trace IDs and spans:
  - start_trace(): Creates a new trace ID
  - span(): Context manager that measures operation duration
  - Tracks parent-child span relationships
  - Records operation status (completed/error)


────────────────────────────────────────
12. ASPECTS (application/aspects/)
    Cross-cutting concerns as decorators (AOP pattern)
────────────────────────────────────────

logging_aspect.py
  @log_operation() decorator:
  - Logs function entry with ▶ and sanitized arguments
  - Logs function exit with ◀ [OK]
  - Logs errors with ✖ [ERROR]
  - Automatically skips sensitive params (password, api_key, token)

metrics_aspect.py
  @track_metrics() decorator:
  - Records operation latency in milliseconds
  - Tracks success/failure counts
  - Uses shared MetricsCollector instance

exception_aspect.py
  @handle_exceptions() decorator:
  - Catches and logs all exceptions
  - Maps exceptions to application-specific types
  - Can return fallback values or re-raise

tracing_aspect.py
  @trace_operation() decorator:
  - Creates a tracing span around the decorated method
  - Records function name, module, and duration
  - Uses shared TraceManager instance


────────────────────────────────────────
13. MESSAGE BUS (application/message_bus/)
    Internal event/command communication
────────────────────────────────────────

broker.py
  Lightweight in-process message broker (Singleton pattern):
  - Commands (1:1): register_handler() + dispatch()
  - Events (1:N): subscribe() + publish()
  - Keeps message history for debugging
  - Thread-safe

commands/analyze_intent.py    — Command DTO to trigger intent analysis
commands/execute_crm.py       — Command DTO to trigger CRM operation
commands/execute_rag.py       — Command DTO to trigger RAG query
commands/generate_response.py — Command DTO to trigger response generation

events/intent_analyzed.py     — Event: intent classification completed
events/crm_completed.py       — Event: CRM operation finished
events/rag_completed.py       — Event: RAG retrieval finished
events/response_ready.py      — Event: final response is ready


────────────────────────────────────────
14. SHARED (application/shared/)
    Common data structures, config, and exceptions
────────────────────────────────────────

configuration/app_config.py
  Centralized configuration using dataclasses:
  - RAGConfig: chunk_size, embedding_model, distance_threshold
  - LLMConfig: provider (gemini/ollama), API keys, model names, temperature
  - CRMConfig: base_url, api_key, timeout
  - DatabaseConfig: MySQL host, port, user, password
  - SessionConfig: TTL, max_history
  - TelegramConfig: bot_token
  - MonitoringConfig: log_level, tracing, metrics
  - AppConfig.from_env(): loads everything from environment variables
  - SUPPORT_FALLBACK_MESSAGE: Arabic fallback directing user to WhatsApp support

dto/chat_message.py
  Incoming user message data class: user_id, text, session_id, platform

dto/chat_response.py
  Outgoing response data class: text, intent, sources_used, confidence
  Has error_response() factory method.

dto/agent_decision.py
  Agent's analysis output: intent, requires (["CRM","RAG"]), parameters,
  confidence, reasoning. Has needs_crm/needs_rag properties.

dto/service_result.py
  Uniform result from any service (CRM/RAG/LLM): source, success, data,
  error, latency_ms. Has failure() factory method.

exceptions/app_exceptions.py
  Exception hierarchy:
  - ChatbotBaseException (base)
  - IntentClassificationError
  - RAGRetrievalError
  - CRMConnectionError
  - LLMInferenceError
  - SessionNotFoundError
  - ServiceTimeoutError
  - ConfigurationError
  - DatabaseError


================================================================================
PART 2 — FULL MESSAGE SCENARIO (INPUT TO OUTPUT)
================================================================================

SCENARIO: A user on Telegram sends "الانترنت بطيء عندي" (My internet is slow)

────────────────────────────────────────
STEP 0: STARTUP (happens once before any messages)
────────────────────────────────────────

  1. app.py main() parses CLI args, creates AppConfig.from_env()
  2. Application.start() creates ChatbotFacade(config) and calls initialize()
  3. ChatbotFacade.__init__():
     - Creates SessionService (tries MySQL, falls back to memory)
     - Creates AgentService (with IntentClassifier inside)
     - Creates RAGService, CRMService, LLMService, ResponseService, AnalyticsService
     - Creates ServiceDispatcher wiring RAG+CRM+LLM
     - Creates WorkflowCoordinator wrapping the dispatcher
     - Wires LLMService into AgentService for smart classification
     - Creates MessageBroker
  4. ChatbotFacade.initialize():
     - RAGService loads chatbot.xls → chunks → embeds → stores in ChromaDB
     - LLM health check (verifies Gemini API is reachable)
  5. If Telegram mode: TelegramBot starts polling for messages

────────────────────────────────────────
STEP 1: MESSAGE ARRIVES
────────────────────────────────────────

  User sends: "الانترنت بطيء عندي"

  → TelegramBot._handle_message() receives the Telegram Update
  → Extracts user_id (Telegram numeric ID) and message_text
  → Sends "typing..." indicator to the chat
  → Calls: facade.handle_message(user_id, "الانترنت بطيء عندي")

────────────────────────────────────────
STEP 2: SESSION MANAGEMENT (inside ChatbotFacade.handle_message)
────────────────────────────────────────

  → SessionService.get_or_create_session(user_id)
  → Checks in-memory cache for existing session
  → If found and not expired: reuses it
  → If not found: creates new ConversationContext with unique UUID
  → Persists session to MySQL (INSERT INTO sessions...)
  → session.add_message("user", "الانترنت بطيء عندي")
  → Message added to session history list

  Result: ConversationContext object with session_id, user_id, history

────────────────────────────────────────
STEP 3: AGENT ANALYSIS (Intent Classification)
────────────────────────────────────────

  → AgentService.analyze("الانترنت بطيء عندي", context)
  → Context includes: session_id, customer_id, last 3 messages

  → IntentClassifier.classify_decision() is called:

    a) First checks greetings/goodbyes — "الانترنت بطيء عندي" is NOT a greeting
    
    b) LLM-based classification (primary path):
       - Builds a prompt:
         "You are an AI router for an ISP chatbot.
          ALLOWED INTENTS: [services, dsl_troubleshooting, billing, ...]
          SERVICES RULES: Include RAG if FAQ/troubleshooting needed...
          User Message: "الانترنت بطيء عندي"
          Respond with JSON..."
       
       - Calls LLMService.generate_raw(prompt)
       - LLM returns: {"intent": "dsl_troubleshooting", "requires": ["RAG"],
                        "reasoning": "User reports slow internet, needs troubleshooting guide"}
       - Parses JSON, validates intent is in ALLOWED_INTENTS ✓

    c) Result: intent="dsl_troubleshooting", requires=["RAG"], confidence=0.85

  → AgentService extracts parameters: {customer_id: "C001", query: "الانترنت بطيء عندي"}
  
  → Creates AgentDecision:
      intent = "dsl_troubleshooting"
      requires = ["RAG"]
      parameters = {customer_id: "C001", query: "الانترنت بطيء عندي"}
      confidence = 0.85
      reasoning = "User reports slow internet..."

  → MessageBroker publishes IntentAnalyzedEvent
  → Session intent updated to "dsl_troubleshooting"

────────────────────────────────────────
STEP 4: WORKFLOW EXECUTION (RAG retrieval + LLM generation)
────────────────────────────────────────

  → WorkflowCoordinator.execute_workflow(decision, user_message)

  → decision.requires = ["RAG"] (not empty, so NOT a greeting)
  → decision.needs_rag = True
  → decision.needs_crm = False

  4a) RAG RETRIEVAL:
      → ServiceDispatcher.dispatch_rag("الانترنت بطيء عندي")
      → RAGService.query("الانترنت بطيء عندي")
      
      → DocumentRetriever.retrieve():
        - Encodes query: embedding_model.encode("query: الانترنت بطيء عندي")
        - Queries ChromaDB for 2 nearest chunks
        - Returns: {
            documents: ["...troubleshooting steps about slow internet...",
                        "...DSL line check procedures..."],
            distances: [0.45, 0.72],
            ids: ["12", "15"]
          }
      
      → Reranker.rerank():
        - Both distances < 25.0 threshold → both pass
        - Sorted by distance: [(doc1, 0.45), (doc2, 0.72)]
      
      → ContextBuilder.build_context():
        - Concatenates documents up to 1500 chars
        - Returns: "...troubleshooting steps...\n\n...DSL line check..."
      
      → RAG returns ServiceResult(source="RAG", success=True,
           data={context: "...", documents: [...], distances: [...]})

  4b) LLM RESPONSE GENERATION:
      → WorkflowCoordinator._generate_llm_answer()
      → rag_context exists, crm_data is empty → RAG-only path
      
      → ServiceDispatcher.dispatch_llm_rag(question, context)
      → LLMService.generate_rag_answer("الانترنت بطيء عندي", rag_context)
      
      → PromptBuilder.build_rag_prompt():
        Creates Arabic prompt:
        "أنت مساعد ذكي لشركة إنترنت هايبرنت...
         السياق: [retrieved troubleshooting content]
         السؤال: الانترنت بطيء عندي
         الإجابة:"
      
      → InferenceEngine.infer(prompt)
      → GeminiProvider.generate(prompt):
        - Sends HTTP POST to Gemini API
        - Receives response with generated Arabic text
      
      → OutputParser.parse_response():
        - Strips "الإجابة:" prefix
        - Cleans up newlines
        - Returns clean answer text
      
      → LLM answer: "يمكنك تجربة الخطوات التالية:
         1. أعد تشغيل الراوتر
         2. تحقق من توصيلات الكيبل
         3. إذا استمرت المشكلة، يرجى التواصل مع الدعم "

  → WorkflowCoordinator returns:
      {
        rag_result: ServiceResult(success=True, data={context: "..."}),
        crm_result: None,
        llm_answer: "يمكنك تجربة الخطوات التالية:..."
      }

────────────────────────────────────────
STEP 5: RESPONSE BUILDING & FORMATTING
────────────────────────────────────────

  → ResponseService.generate(session_id, intent, llm_answer, rag_result, None)
  
  → ResponseBuilder.build():
    - llm_answer is not empty → uses it directly as response text
  
  → ResponseFormatter.format_for_telegram():
    - Strips whitespace
    - Checks length < 4000 chars ✓
  
  → Determines sources: ["RAG", "LLM"]
  
  → Returns ChatResponse:
      session_id = "abc-123-..."
      text = "يمكنك تجربة الخطوات التالية:..."
      intent = "dsl_troubleshooting"
      sources_used = ["RAG", "LLM"]

────────────────────────────────────────
STEP 6: POST-PROCESSING
────────────────────────────────────────

  → session.add_assistant_message(text, intent, sources)
    - Adds bot reply to conversation history with metadata
  
  → AnalyticsService.record_interaction():
    - UsageMetrics increments total_queries
    - Increments dsl_troubleshooting intent counter
    - Increments RAG and LLM service call counters
    - Records per-session stats
  
  → MessageBroker publishes ResponseReadyEvent
  
  → Logs: "Response generated in 1250ms | Intent: dsl_troubleshooting |
           Sources: ['RAG', 'LLM']"

────────────────────────────────────────
STEP 7: DELIVERY TO USER
────────────────────────────────────────

  → ChatbotFacade.handle_message() returns ChatResponse to TelegramBot
  
  → TelegramBot._handle_message():
    - Calls: update.message.reply_text(response.text)
    - Telegram API sends the Arabic response back to the user's chat
  
  → User sees:
    "يمكنك تجربة الخطوات التالية:
     1. أعد تشغيل الراوتر
     2. تحقق من توصيلات الكيبل
     3. إذا استمرت المشكلة، يرجى التواصل مع الدعم "

CROSS-CUTTING CONCERNS (applied via decorators throughout the flow)

  @track_metrics()     → Records latency + success/failure counts
